## The one thing worth knowing before planning around it

**#558 is closed, but its throughput claim was never measured.** The mechanism
is tested: sockets bind, the port set is negotiated, clients spread across it,
and both halves fail their test when reverted. Whether that lifts the per-broker
ceiling is unproven. The acceptance criterion was the receive path falling from
~88% of one core toward ~88/N, and nobody has run it.

No developer machine can answer it either (#597): a single generator process is
capped by one client I/O thread, so every local sweep comes back flat whatever
the change does. It needs Linux and separate generator machines.

When that session happens, two things matter:

- Measure `FELIX_IO_RUNTIME_THREADS` at 0 and at N+2, not just the default.
  On two brokers a pool of 2 measured 1,341 MB/s against 1,896 with the pool
  off. A run that uses the wrong value reports no improvement, and that reads
  as a verdict on the feature.
- Watch for a decline with listener count. Local runs drifted 543 → 485 MB/s as
  listeners rose. That is inside the noise of a rig that could not measure
  anything reliably, but if it reproduces somewhere trustworthy, N endpoints
  have a cost worth knowing.

## Waiting on a decision

**#601** — a control-plane instance reports ready before its replicated state
is current. Its guard is `last_log == 0`, which a member escapes as soon as it
accepts one entry, while the remaining lag check measures it against its own
log. A member holding one entry of a thousand reads as caught up.

Fixing it means deciding what "current enough to serve" is when readiness may
not cost a consensus round trip. That trades availability against serving a
stale or empty world, and the present bound was chosen deliberately. #603
makes the resulting answer honest without closing the window.

## Things that cost time this week

- **Three issues had stale premises.** #527's defect was fixed a week before it
  was filed, #536 said the client computes `shard_for` when it could not, and
  #532's "no timeout scaling anywhere" was already false. Read the code before
  implementing an issue in this backlog.
- **`raft_chaos` and `consumer_groups::a_group_position_survives_a_leader_failover`
  fail under CI load and pass alone.** That is five tests now in the same shape:
  a fixed wall-clock budget on a setup wait. Worth fixing as a class.
- **Adding a dependency to `controlplane` changes the demo lockfiles**, because
  the demos depend on it by path and sit outside the workspace. CI fails on it.
  `task lock:refresh` is the fix, and it belongs in the release bump.
